# Research SSH workspace (preview)

Research conversations can use a local Codex session with a saved SSH server. Add the server in the existing SSH server settings, select Codex and Research, then use the server icon next to the local workspace in the composer to select the server. The icon marks a selected server; its menu shows the server and remote directory. Use an approval-enabled Codex permission mode. Existing Codex sessions without SSH dynamic tools can use a per-turn local CLI bridge without changing the native session or importing its visible transcript. The bridge currently requires macOS or Linux and a local workspace that permits an `.archimedes` directory.

Codex runs on the local machine and retains its native conversation, context and permission handling. When asked to work remotely, it can call `ssh_remote_read`, `ssh_remote_edit` and `ssh_remote_exec` dynamic tools, or use the per-turn CLI bridge when its session does not have those tools. File reads are limited to 200 lines and 24 KiB per call. Edits operate on an existing UTF-8 file up to 1 MiB and require a unique exact match; the approval shows the old and new text. Creating files and other operations use the command tool. File tools require Python 3 on the remote host. Each operation displays its target, directory and action for approval before execution. Codex's ordinary file and shell tools still operate locally; this is not transparent redirection of all native tools. The selected server resets when opening a different conversation and must be selected again.

An SSH shell command waits for you to review the host, directory, and command and click **Run**. **Dismiss** rejects the request. The SSH read and edit tools still request approval separately. Selecting an SSH server identifies the target for future requests.

Remote commands are not Archimedes-managed experiment Runs and do not automatically create Research Graph evidence. Reproduce remains separate. Commands time out after 60 seconds and their output is bounded; cancellation, timeout or a connection failure does not prove that the remote process stopped. Inspect the server before retrying. Persistent SSH connection reuse, automatic reconnection, long-running job management, remote run tracking and reproducible snapshots are not implemented here. Host-key behavior follows the existing SSH server connection settings. The saved server's Docker setting is for Reproduce and is not used by this workspace: operations run on the SSH host.

A real temporary Codex session used the read, edit and read tools on an isolated remote fixture; the fixture was removed afterward. The user's original conversation was not used for this smoke test.
